## Deployment and rollback

The release was built as named-file overlays of the recorded serving ZIPs, preserving native dependencies, entrypoints and each worker variant's consent integration. The deploy tool refuses code/revision drift and requires matching startup-test hashes. Each upload retained an immutable rollback ZIP/configuration and verified the resulting code hash and unchanged runtime settings. This avoids redeploying an older local checkout over unrelated production work.

Deployed functions: SavedRecipeStatus, SavedRecipesApi, KitchenApi, MealPlanGenerator, MealPlanApi, all three quick-ack worker entrypoints, iMessage context projection and UX failure monitor. Exact names, UTC times and hashes are recorded in `test-results.json` and private deployment receipts.

The additive generation-queue/publication schema was verified before use. The retry stack `trepo-meal-plan-retry-20261023` was installed disabled, tested, then enabled and verified `UPDATE_COMPLETE`. Its dispatcher has no model key and only invokes the existing consent-guarded generator. Monitor access is scoped to the required tables/media prefixes and metrics; missing objects are distinguished from read-denied coverage gaps.

For rollback, disable new dispatch first, then use the exact recorded prior package/revision after accounting for in-flight workers. Keep additive tables and receipt evidence. Never restore an old database snapshot over customer edits. Reversing an individual correction requires matching its post-correction revision; do not replay whole voice utterances or duplicate completed shopping actions.
